# Bug sweep — every folder and file, 2026-10-18

Tool: `node scratch/audit_repo.js` (re-runnable). It walks the tree — 434 JS files, 10,150 JSON files
under the 2 MB limit, 11 HTML files — and checks five things a code change can plausibly break:

1. **PARSE** — the file cannot be compiled at all.
2. **REQUIRE** — a `require()` pointing at a file or package that is not there.
3. **JSON** — a data file that no longer parses.
4. **DUPLICATE-DECL** — two declarations of one top-level name (a SyntaxError from a double edit).
5. **STALE-STRATEGY** — live code still naming an engine that is not registered.

1742 JSON files larger than 2 MB were counted, not parsed: the `data/` corpora total 10.7 GB
(`signal_ledger.json` alone is 66 MB) and parsing them is not a code check — it is also what made the
first two runs of this sweep time out.

## Fixed during the sweep

**1. `strategy-core/engines.js` could not load — the whole app was down.**
The registry had been rewritten to:

```js
key: 'GB06',
mod: gb06,        // no require for gb06 anywhere in the file
```

`ReferenceError: gb06 is not defined` at `Module._compile`, which takes down every consumer:
`Server.js`, `strategy-core/strategyLedger.js`, `scripts/buildBoard.js` and the test suite. Restored
to the two registered engines (FVG/FG01 = GB01, ORDERFLOW/OF03 = GB03a) with the full export surface
(`ENGINES, BY_KEY, MAX_HOLD, FRAME_LABELS, frameLabel, hhmm, hhmmOfClock, MIN_NET_PF,
MIN_TRADES_FOR_SAMPLE, measuredRules, catalogue`). The overwritten version is preserved at
`scratch/engines.concurrent-overwrite-2303.bak` — it also re-registered GB02, SWING and CODEX, which
were removed earlier the same day, so the two changes are in direct conflict and someone has to win.

This was the **third** breakage of that one file today: twice an undefined `gb06`, once truncated at
90 lines with no `]`, no helpers and no exports. It is rewritten by `scratch/fix_engines.js`, which
splices text between `const ENGINES = [` and `const BY_KEY = {};` — if either marker is missing at
the moment the script runs, the slice is wrong or partial.

**2. `test/positionSizing.test.js` — two assertions were wrong, not the module.**
`lotSize` rounding and the "risk budget below one share" case were both written with arithmetic that
did not match the inputs. Corrected to cases that isolate the rule (200 shares = 8 whole lots; a ₹5
budget against a ₹10 stop distance). Both now pin the intended behaviour: `9/9` pass.

### Invalid JSON — written with `NaN` / `Infinity`

`JSON.parse` refuses these, so any reader of these artifacts throws:

- `backtest/f1/results_discovery.json` — `"sd": NaN`
- `backtest/f1/results_heldout.json` — `"sd": NaN`
- `research/mechanism-discovery/ar1_results.json` — `"gross_pf": Infinity`
- `research/mechanism-discovery/i1_results.json` — `"net_pf": Infinity`

Cause is at the writer: Python's `json.dump` emits bare `NaN`/`Infinity` unless
`allow_nan=False`. A reader should either stop producing them or the writer should coerce to `null`
(`Infinity` in a profit factor means "no losing trades measured", which is a real state and belongs
as `null` + a note, not as invalid JSON).

### Encoding

`create_clean_page.js` (repo root) is **UTF-16 LE with a BOM** (`FF FE`), so `node
create_clean_page.js` fails with `SyntaxError: Invalid or unexpected token`. Node only loads UTF-8
source. Nothing references it.

## Notes on the sweep itself

Two early versions of the checker reported **15 phantom PARSE errors** and ~100 phantom REQUIRE
errors. They were the tool's fault, and both causes are worth keeping in mind for any future static
check: `new Function(src)` rejects a UTF-8 BOM and a `#!/usr/bin/env node` shebang that Node's own
loader strips, and a `require(...)` written inside a JSDoc example is documentation, not a
dependency. The harness now strips the BOM, strips a leading shebang, and removes comments before
scanning — which is why the final report has 1 parse error instead of 16.
