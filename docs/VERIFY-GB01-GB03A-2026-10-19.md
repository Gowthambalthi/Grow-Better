## 3. BUG — live GB03a evaluates a 9-second-old bar, so its first gate cannot pass

> **REPAIRED 2026-10-19 (after the session).** The rule below is now the rule that runs:
> `strategies/orderflow/liveMinuteEngine.js` feeds the OF03 engine the newest bar whose minute has
> **ended**, walks every closed bar in between in order, and keys "already fed" on the bar's own
> timestamp — the same rule, deliberately, as `strategies/fvg/liveAdapter.js`, which never had this
> defect. The funnel also publishes `gb03.evaluated` now, so "nothing set up" and "never reached"
> are no longer the same reading. Pinned by `test/of03ClosedBar.test.js` (five tests). This section
> is left standing as the measurement that found it.

The live scan fires at a fixed offset from boot; today it ran at **`hh:mm:09`** all session
(funnel `asOfIST: 14:28:09`, logs `Minute Scan (14:28:09 IST)`). At that moment:

- `ingestTick()` has already opened the new minute's bar, so `symBars[-1]` is the **forming** bar;
- the OF03 branch calls `ofEng.onBar(formatted, formatted.length - 1)` on that array — the forming
  bar is the one being evaluated;
- `strategies/orderFlow.js` gates participation first:
  `if (market.volumeRatio < cfg.of03MinVolRatio /* 1.7 */) return null;`
- `volumeRatio` = *this bar's* volume ÷ the average of the previous 20 bars
  (`strategy-core/indicators.js:171`).

Measured on the 2026-10-19 tape (61,936 symbol-minutes with a full 20-minute history):

| how the bar is read | `volumeRatio ≥ 1.7` | mean ratio |
|---|---|---|
| **first 9 seconds** (what live sees) | **1.106%** | **0.165** |
| **full minute** (what the backtest sees) | **15.813%** | — |

The first 9 seconds carry **14.3%** of a minute's volume in aggregate (median 9.1%, p90 40.0%). A
9-second bar therefore needs to be ~12× a normal minute's rate to clear 1.7, and it clears on
**1 in 90** symbol-minutes instead of **1 in 6** — a **14×** handicap before any of the other
conditions (new extreme, close location, 3-bar confirmation, RR) are applied. The measured engine
would make 25 trades in 705 sessions; this path makes approximately none, which is exactly what the
call book shows.

**Why GB01 is not affected:** `strategies/fvg/liveAdapter.js` rule 1 refuses to feed a bar until
`now >= bar.t + 60s`. The adapter is correct; the OF03 branch was missing the same guard. The repair
(now in place, §3 above) hands the engine the last **closed** bar — and every closed bar before it,
oldest first, each exactly once — exactly as the harness does.

### 3b. CORRECTION — the 14x in §3 overstates the defect, and it was NOT why the book was empty

§3 measured the gate two ways **with a mixed denominator**: a 9-second numerator (`1.106%`) against
the same 20-bar average the full-minute reading uses (`15.813%`). That is not what the live engine
experiences. `volumeRatio` is the bar's own volume over the PREVIOUS 20 BARS, and after ~20 minutes
of scanning every one of those bars was handed over by the same branch, partial in the same way — a
ratio against its own recession, which largely cancels. The `15.813%` reading is a statistic about a
mixture live never ran.

Measured directly instead, on the 2026-10-19 tape
(`scratch/gb03_live_vs_forming_2026-10-19.js`, 494 symbols, 3.8M ticks, the SHIPPING engine and
registry config in both arms, each bar fed once in order):

| arm | OF03 emissions | refused by the planner | with a plan |
|---|---|---|---|
| **closed bars** (harness; the repaired live branch) | **53** | 47 RR · 6 EXTENSION | **0** |
| **the forming 9-second bar** (what live did) | **51** | 46 RR · 5 EXTENSION | **0** |

The two arms differ at the symbol level (54 of the 72 symbols with any emission differ in count) but
not in total, and **neither produced a single call**. So:

- the 2026-10-19 empty book was **the planner refusing all 53 emissions** — the RR gate above all —
  which is the base rate this setup is measured to have: 25 planned trades per 705 sessions per 100
  symbols, i.e. ~0.18 calls for a 494-name session. It was not a dead feed and not a 14x handicap;
- §3's mechanism (a fragment bar deciding) is still real and worth repairing — the bar's high, low
  and close-location were nine-second fragments, and a call armed off that geometry is not a call the
  backtest scored — but the repair is **parity**, and it changes nothing about today's count.

One consequence for the report that hid this: the live funnel stayed `null` all day because it only
counted an OF03 outcome that reached `ok` or a refused SIDE. An emission refused by the PLANNER was
counted nowhere, so "the planner said no 53 times" read exactly like "the engine was never reached".
That is repaired with this finding: `getScanFunnel().gb03` now carries `evaluated` (symbols whose
closed bar was handed to the engine), `refusedPlanner` and `refusedGates` (by gate name), so the next
quiet day states which of the three happened. Pinned in `test/of03ClosedBar.test.js`.

Same mechanism, milder, affects `OF_MOMENTUM`: its VWAP band, delta and vol surge are computed with
the 9-second bar as the newest bar, so its live arithmetic is not the arithmetic the tape replay
scored.

## 4. GATE MISMATCH — live GB03a is shorts-only, the quoted number is both sides

`GB03_SIDES` defaults to `short` (`strategies/orderflow/liveMinuteEngine.js`). The engine still
evaluates both sides; the live boundary refuses longs, and counts the refusal.

So the rule that runs is the **13-trade / +19.3R / netPF 4.086** short arm — which is a better
number than the board's — while the board row quotes **25 trades / netPF 1.997**, a configuration
that cannot trade. It is not a wrong number, it is a number for a strategy that is not running. The
row should say "shorts only" or quote the 13-trade arm.

Windows and configuration are otherwise **consistent**: both paths read
`BUY`-side `maxSignalTime: 1230` from `strategy-core/engines.js` (`runAll` calls
`createEngine(engine.config)`, live spreads `OF03_CONFIG`), both apply the same
`BLOCKED_WINDOWS` (12:15–12:45, 13:15–13:45) before building candidates, and the FVG engine's own
14:45 cutoff is the same object in both. `pickStopGeometry()` is byte-identical to the 2026-10-14
snapshot.

## 5. BUG — the canonical artifact was overwritten with one engine, and GB01 vanished from the board

`data/terminal/backtest_results.json` (written **2026-10-19 12:17**) contains **`ORDERFLOW` only**:

```
ORDERFLOW  trades 25  netPF 1.997  netR 15.97
```

`strategy-core/engines.measuredRules()` reads that file, so the board now computes:

```
[ { trades: 0,    netPF: null },      ← FVG / GB01
  { trades: 25,   netPF: 1.99694 } ]  ← ORDERFLOW / GB03a
```

GB01 is silently published as *zero trades*. This is the **second** occurrence of the incident
recorded in `GB-CROSSCHECK-2026-10-18.md` §"the artifact had lost the engine". The runner's own
guard (`--out` defaults to the canonical path; windowed runs go to `scratch/`) does not stop a
single-engine run (`--engine=ORDERFLOW`) from rewriting the record.

Repair is a full three-engine run written with `--out=data/terminal/backtest_results.json` (the
2026-10-18 artifact was regenerated exactly this way). **Not done here** — it replaces the shipped
record, which is a call for you, not a verification step.

## 7. Limitations

- The live record covers 16 sessions and only three writers; absence of GB01/GB03a calls is evidence
  about *this* book, not proof they never fired before it existed.
- The 9-second measurement uses one tape (2026-10-19) and 1.5M ticks; the offset is set by process
  boot, so a restart at another second changes it (the fix must not depend on the offset).
- Backtest reproduction is on 100 symbols; the full 1,031-symbol corpus is not re-run here.
- `data/terminal/backtest_results.json` was **read, not written**.

## 8. The "0 stocks scanned · 12:30" report (found during this audit, fixed)

The 12:30 Telegram report read `0 stocks scanned / 0 in play · 0 qualified` and looked like a dead
feed. It was not: it came from a **Server instance started at ~12:14:51**, i.e. inside the
12:15–12:45 no-entry window.

Evidence:

- the funnel file has scans at 12:10:46, 12:11:46, 12:13:14, 12:14:15 and then **nothing until
  12:45:12** — the blocked-window return, working as designed;
- `logs/server-scansummary-2026-10-19b.log` (the process that started ~12:14:51) contains **zero**
  `Minute Scan` lines — it pre-loaded 17,41,002 ticks and never got to walk the universe;
- the message carries no `· last pass …` suffix, which is the tell: `asOfIST` was null.

`emptyFunnel()` is every counter at zero *and* no timestamp, but `formatScanSummary` only treated
`scanned == null` as "no pass yet" — so a never-scanned engine printed `**0** stocks scanned`, the
exact opposite of what the field means. The old test pinned that behaviour as if a zero-count pass
were the same thing.

**Fixed:** a pass now has to carry its own `asOfIST` to be reported as a count; the empty funnel
renders "No symbol-level scan has walked the universe yet in this process", and a genuinely empty
pass (timestamp present) still reports 0 with its time. `test/scanSummary.test.js` pins both cases
(10/10 pass).

**Still open:** any second Server instance runs the scheduler and can message the owner — this
report came from a short-lived process, not the main one. A single-instance guard (or a scheduler
that refuses to run without a successful `listen()`) would remove that class of false report.
